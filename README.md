# Eya

Windows-first AI desktop agent. Local-first where it can be, Gemini where it helps. Electron + TypeScript strict.

## What it does

- **Hears you on your own PC.** Always-on listening: voice-activity detection cuts real utterances out of the mic, and an on-device Whisper model (`whisper-tiny.en`, ~43 MB, downloaded once from Hugging Face and cached) turns them into text. Simple commands ("open Notepad") are then handled locally with **no cloud call at all**. Until the model has loaded, or if it fails, speech goes to Gemini instead. On first use it also times your graphics chip against your processor (a few seconds, once) and keeps whichever transcribes faster; an Intel UHG-class chip typically wins by about 2x.
- **A real wake word.** Saying "hey Eya" is recognized as *sound*, not by waiting for a whole sentence to be transcribed: a small always-on keyword-spotting model (~41 MB, downloaded once) listens continuously and opens Talk mode the moment it hears the name. If it misses (it catches roughly half of attempts by itself), the existing text-based check still catches most of the rest a moment later, once the utterance is transcribed — the two run side by side and either can start the conversation.
- **One voice button.** Listening and speaking are switched on and off together, and Eya goes silent immediately when you turn it off.
- **Talk mode (Gemini Live).** The **Talk** button, or just saying "Hey Eya", opens a real-time spoken conversation: Gemini's own voice, low latency, tools available mid-conversation. It ends when you press the button again, say so, or after a quiet spell. Only "Hey Eya" (or the name however it is misheard) starts it; a command such as "Hey Eya, open Notepad" is still handled as a plain command.
- **Interrupt her.** The **Interrupt** pill (on by default) lets you talk over Eya mid-sentence in Talk mode and have her stop and listen, the way a phone call works. Turn it off if your microphone picks up her own voice from the speakers and she ends up interrupting herself.
- **A natural voice, your choice of 13.** Outside Talk mode Gemini's speech models stream audio in about a second. Replies heard before are saved and play instantly. Pick from 8 female and 5 male voices in the panel's dropdown, grouped by gender — the five male voices are curated personas (warm/friendly, deep/calm, professional, young/energetic, natural/conversational), each confirmed live on both the streaming voice API and the Live conversation API before being added. If the cloud voice is unavailable it falls back to the offline Kokoro voice, then the Windows voice.
- **Multi-step tasks.** "Find my latest PDF in Downloads, read it and tell me the hearing date" chains tools: the model picks a tool, gets the result, and repeats until it has an answer (typed/agent path: max 16 steps / 90 s — a website task can genuinely need more back-and-forth than a file search ever did, since the number of steps depends on what the live page actually shows at each one, not a fixed count). If a step takes more than a couple of seconds Eya says "Working on it." (in Talk mode a Live tool call is also given up on after 40 s, and Eya says it took too long).
- **Instant simple commands.** "Hey Eya, could you please open Notepad?" is matched locally.
- **Can actually change things now, carefully.** Eya can create folders, copy, move, rename and delete files and folders — chained together, e.g. "find my latest PDF, create a folder called Cases on my Desktop, and put it there." Nothing that deletes or overwrites something ever happens on the first ask: the tool returns the question instead of acting, Eya asks it out loud, and only your next clear yes makes her do it. "It", "that file" and "the folder" resolve to whatever was most recently found or touched, across separate requests, not just within one sentence.
- **A real Recycle Bin, not a lookalike.** Eya can list what's actually in it, search it by name or by when something was deleted, restore one item or everything that's safe to restore, permanently delete a single item, or empty the whole bin — always against the real Windows Recycle Bin, never a separate list of her own. Restoring refuses if the original location is outside your user folder or something already occupies that name; emptying the bin always asks first, stating exactly how many items and how much space it would clear.
- **Searches your whole PC, not just Downloads.** "Play Con City", "open my petition PDF" — unless you name a folder, Eya searches your entire user folder plus every connected drive, never just Downloads/Desktop/Documents. Windows' own file index answers most of these instantly; a real, slightly slower search of every drive runs alongside it regardless, so a file the index doesn't know about (a second drive, say) is never silently missed. Beyond name and type: "find PDFs from yesterday", "find images larger than 5 MB", "find Word files modified this week". If several files match what you're about to act on, Eya lists the actual names — and where each one is, if they're in different places — and asks which one rather than guessing; once she's listed them, "the second one" or "the cause list one" correctly picks from that exact list, even in a later, separate request.
- **"Play" a file, wherever it is.** There's no separate play tool: "play Con City" finds the video, then opens it in your default player, the same way opening any file does. A file Eya finds outside your own user folder (another drive, a folder like `C:\Movies`) can be opened, played or read exactly like one inside it.
- **Closes the document, not the app.** "Close report.docx", "close that PDF", "close it" (right after opening something) close just that document's window — the application stays open if you have other documents in it. "Close Word" still closes the whole app; Eya tells the two apart from how you ask.
- **A few Windows settings, directly.** "What's my volume?", "set the brightness to 40 percent", "mute", "open the display settings page" — verified against the actual system state after each change, not just assumed. Deliberately not included: turning Wi-Fi or Bluetooth on/off (see Safety).
- **Lock, restart and shut down — for real, not a Settings page.** "Lock my screen" actually locks Windows right now, the same as Win+L, with no confirmation needed. "Restart" and "shut down" actually do it, always asking first since they affect every open application, not just Eya — and never force-close anything, so an app with unsaved work gets to ask you itself, the same polite rule closing an app already follows.
- **Opens the real application, not a search.** "Open WhatsApp" looks the app up the way Windows' own Start Menu search would — ordinary installed programs and Microsoft Store/UWP apps alike — and launches the real thing if it's there, not a guess or a browser tab. Only if nothing is genuinely installed does it fall back to a well-known official web app (WhatsApp, Telegram, Discord, Spotify) opened in whichever browser already looks actively in use, rather than launching a different one; if there's neither an installed app nor a known web version, Eya says so plainly instead of searching the web for it.
- **Navigates an actual website, instead of guessing a URL or searching for it.** "Open the High Court of Telangana website and go to Cause List" opens the real site (searching the web only to confirm its URL, once), then looks at what's genuinely on the page and clicks the real "Cause List" link — never "go to Cause List" turned into a Google search, and never an invented address. Works the same way for any website — a store's orders page, an inbox's Sent folder, a code host's repositories — since it looks at the actual page each time rather than assuming how one is laid out. If what you asked for isn't visible, Eya says what actually is there instead of guessing, and a multi-step conversation ("Cause List is open — which kind?" / "Advocate Code Wise" / "21295") keeps using that same page.
- **Works in your own, already-signed-in browser — and only there, unless you say otherwise.** Say "connect my browser" once and add the small Eya Browser Bridge extension (`eya-chrome-extension/`, a one-time "Load unpacked" in Chrome and/or Edge; both can be connected at the same time). From then on every website task runs in *your* browser — your real profile, tabs and sign-ins. Eya reuses a tab you already have open on the site, otherwise opens a new tab in the same browser, otherwise starts your normal browser; when both Chrome and Edge are open she uses the one that actually has the site. She never quietly opens a separate, signed-out automation window: if your browser isn't connected she says so and why. Every action ends with a fresh look at the page (what appeared, what changed, a new tab it opened, a file it downloaded), she notices when *you* change something in the browser meanwhile, and when a page needs you to sign in or pass a check she waits, then carries on with your original request without being asked again. She stops and asks whenever a page shows a CAPTCHA or asks for a code, never types passwords or card numbers, and asks before anything that would buy, send, delete or change an account setting. See "Using your own signed-in browser" below.

### Safety

- **Finding, opening, playing and reading a file reaches your whole PC; changing one stays inside your user folder.** `find_file`, `open_file`, `open_folder`, `read_file` and `analyze_document` can reach anywhere accessible — your own folder, any other connected drive — but `create_folder`, `copy_file`, `move_file`, `rename_file`, `delete_file` and `delete_folder` still only ever touch something inside your own user folder, unchanged. Secrets are blocked everywhere either way (`.env`, `.ssh`, `AppData`, `*.pem`, `credentials.json`, ...), including this project's own `.env`, and so are Windows/program internals (`C:\Windows`, `Program Files`, `$Recycle.Bin`, ...) and another Windows account's own profile — Eya only ever sees what you, this account, could see in File Explorer.
- Programs and scripts (`.exe`, `.ps1`, `.lnk`, ...) are never opened.
- Closing apps is polite: Eya asks the window to close and reports honestly if it stays open (for example "save changes?"). She never force-kills anything except Calculator, which ignores polite requests and has nothing to lose. Explorer windows are closed individually, never by ending `explorer.exe`, so your desktop and taskbar are untouched.
- Text inside files, web pages and the clipboard is treated as information, never instructions.
- **Delete or overwrite always asks first, out loud, and nothing else can skip that.** The tool itself refuses to act on the first call — it hands back a plain question instead of a result. Eya can only proceed once she calls the same tool again with an explicit "the user agreed" flag, which the model is instructed to set only after you've clearly said yes in that same conversation. This lives in the tool's own logic, not in a prompt the model could just ignore.
- **Deleting always offers a real choice, never just permanent.** "Do you want me to delete X normally, so it goes to the Recycle Bin, or permanently delete it?" — a normal delete genuinely uses the Windows Shell's own Recycle Bin mechanism (`Microsoft.VisualBasic.FileIO.FileSystem`, the same one behind Explorer's own Delete), not a lookalike; a permanent delete is the only one that skips it. Verified live, both ways, checking the real Recycle Bin's contents afterward.
- **Recycle Bin tools work against the real Recycle Bin.** Listing, counting (`SHQueryRecycleBin`), restoring and deleting all read and change the actual per-drive `$Recycle.Bin` contents — never a separate list Eya keeps herself. Restoring re-checks the same folder boundary as any other file write (refuses outside your user folder, or if something already occupies that name); permanently deleting an item already in the bin, and emptying the whole bin, skip that particular check since the item is already on its way out regardless — but emptying always asks first, stating the real count and size, and only proceeds on an explicit yes.
- `delete_folder` will not touch Desktop, Downloads, Documents, or any other of your main folders, whatever else is asked of it — only something inside them.
- Every create/copy/move/rename/delete is verified after the fact by actually checking the filesystem, not just trusting that the call didn't throw.
- A bare file or folder name (not a full path) can never contain `/`, `\`, or `..`, so a name argument can't be used to sneak outside the folder it was given for.
- Eya still cannot send, install, or purchase anything.
- `analyze_document` uploads the file to Gemini to read it; that is inherent to the feature.
- **No Wi-Fi/Bluetooth toggle tools, on purpose.** Turning off the machine's own Wi-Fi adapter risks cutting off the PC Eya runs on, and turning off Bluetooth risks dropping a wireless mouse or keyboard; both also typically need administrator rights, which Eya doesn't run with. Their Settings *pages* still open on request — flipping the switch is left to you.
- **Restarting or shutting down always asks first, every time, the same as a delete.** The first call does nothing and hands back a plain question; only a clear yes gets a `confirm: true` retry. Neither one force-closes anything — Windows itself asks any application with unsaved work to close first, exactly like `close_application` already does, so a restart can genuinely pause on a "save changes?" prompt in some other program. Locking the screen needs no confirmation: it's reversible with your own password and has nothing to lose.
- **"Open X" only ever launches something real.** Beyond a short built-in list, an unrecognized app name is checked against Windows' own Start Menu registration (the same source its own search uses) — this deliberately excludes uninstallers and documentation/website shortcuts that Windows also lists there, so "open node" can never be misread as "run the Node.js uninstaller". Only when nothing is genuinely installed does a small table of known official web apps get tried, and only in a browser that already looks in active use (several of its processes already running, not just one leftover background helper) or, failing that, your default browser — never a browser you weren't already using. If neither exists, Eya says so instead of guessing or web-searching.
- `close_file` matches a document to a window by its title (e.g. "report.docx - Word"), not full Windows UI Automation — it can't yet tell which of two identically-named documents in different folders is which, and it correctly refuses rather than guessing when more than one open window matches.
- **Website navigation never turns "go to X" into a search, or a guessed URL.** `click_on_page`/`fill_on_page` only ever act on something actually visible on the page that's currently open, found by inspecting it fresh each time — never by remembering how a site "usually" looks or inventing an address. If nothing matches, Eya is told what IS actually there instead of guessing further. Website tasks run in your own Chrome or Edge through the extension. Without it, `open_website` does **not** quietly open a browser of its own: that window starts logged out of everything, which is exactly what you don't want for your own accounts, so Eya says the browser isn't connected (and why) and offers to connect it. Her separate window (Playwright, its own persistent profile in Eya's data folder) is used only when you have agreed to it for that task (`isolated: true`), or if you set `EYA_BROWSER_MODE=eya_browser` / `auto` yourself. If you close that window, the next request simply opens a fresh one.
- **In your own browser, a few more rules apply** (details below): a CAPTCHA / "verify you are human" check / verification-code prompt stops Eya and she asks you to do it; she never types into password, card-number or one-time-code fields and never reports what is in one; a click that would buy something, send or publish something, delete something or change an account setting is not done on the first call — the tool hands back a question, and only your clear yes (`confirm: true`) lets it through; she never navigates away a tab you were using; and if your browser disconnects mid-task she stops and says so instead of carrying on in a different browser behind your back.
- No general system-command tool exists or is planned — every capability here is a specific, typed function, never an arbitrary shell command the model could construct.

## Setup

Prerequisites: Node.js 20+, Windows 10/11, and Chrome and/or Edge installed (Eya doesn't bundle or download a browser). For website tasks, add the Eya Browser Bridge extension to the browser(s) you use once — say "connect my browser", or see `eya-chrome-extension/README.md`. After updating Eya, reload the extension (its version is checked on every connection; an out-of-date one is refused with a plain "reload the extension" message).

```
npm install
copy .env.example .env    # then put your Gemini key in .env
npm run dev
```

The speech model (Whisper tiny.en, ~74 MB) is fetched once by `npm run fetch-models` into `models/` (the `pack` and `dist` scripts do this for you; every file is checked against `scripts/models.lock.json` and a wrong one is refused). Run from source without it, Eya downloads it the first time she starts, as she always did. The wake-word model (~41 MB) lives in this checkout at `models/kws/` and is read straight from disk; it needs the native `sherpa-onnx-node` / `sherpa-onnx-win-x64` files, which the installer carries unpacked. If either fails to load on a given machine, the wake word is simply unavailable and Eya falls back to the text-based name check only (nothing breaks).

Note that `npm run dev` rebuilds the interface live but does **not** restart the main process when you edit it; restart the app after changing anything under `src/main` (this includes wake-word changes, since the model runs in the main process).

## Installing Eya (the Windows installer)

```
npm run dist     # release\Eya-Setup-0.1.0.exe  (~142 MB, a per-user installer: no administrator prompt)
npm run pack     # just the unpacked app, release\win-unpacked\Eya.exe, for testing without installing
```

**What it carries:** the app; the speech model and the wake-word model with its native add-on; the browser-bridge extension folder (`resources\eya-chrome-extension`, for "load unpacked"); and the speech engine's own WebAssembly runtime. The last one matters: the speech library fetches that runtime from a public CDN unless told otherwise, so an installed Eya with no internet had a local model and no engine to run it. It is bundled now (`src/renderer/ortRuntime.ts`).

**No `.env` when installed.** The first thing a new user sees on Home is "Add your Gemini key", and **Settings → Gemini key** is where it goes. The key is checked with Google before it is saved (a wrong one is refused with the reason), saved encrypted by Windows (DPAPI: only this Windows account can read the file), never sent to the page (the page is told only where the key came from and its last four characters), and starts being used the next time Eya starts. A key in the environment or a `.env` file still wins, as it always did; an installed Eya looks for that file beside `Eya.exe` and in her own data folder, and no longer in whatever folder she happened to be started from. Without a key, everything in "Fast everyday commands" still works, along with speech recognition, memory and the file index; the key adds conversation, reading documents and the screen, and the live voice.

**How the installed app was checked** (the unpacked app, started on an empty data folder with the browser's network blocked, so `huggingface.co` and Google were unreachable while Eya's own page and the bundled model still loaded): the page loads and is cross-origin isolated (needed for several-thread speech), the memory database is created, the wake-word model loads, the speech model is ready from the bundle in about 3 s on the processor and upgrades to the graphics chip (1.3 s against 2.8 s for a test clip), the key screen refuses a malformed key, saves a well-formed one encrypted (no plain text in the file) and removes it, and everyday commands are decided in 2–4 ms. That test found the runtime-from-a-CDN bug above, which an earlier run missed because its "offline" switch was mis-quoted and never took effect.

**Honest limits.** The installer is **not code-signed**, so Windows SmartScreen will say "Windows protected your PC" (More info → Run anyway) until it is. There is no update feed: `latest.yml` is generated but nothing serves it, so updating means installing the new setup file. Windows x64 only. The installer itself was built and its contents listed, but not run on this PC; the unpacked app was. The offline *voice* (Kokoro, ~86 MB) is not bundled: with internet it downloads the first time it is needed, and without it Eya speaks with the Windows system voice (the Light level uses the system voice by choice). A real Gemini key was not entered into the installed app (that path is covered by tests and the offline "saved, couldn't check" path, not a live round trip).

## Important: Gemini limits

A free Google AI Studio key has **daily request limits per model**, and the preview models are often "overloaded". A voice assistant spends requests quickly, so on the free tier you can run out mid-day. When that happens Eya says so, **and when it comes back** ("I've used up today's free Gemini limit, so I can't do that until it comes back at 5:30 AM tomorrow. Try again after that, or turn on billing in Google AI Studio and it works straight away") — in *your* clock time, from Google's own stated wait: measured against the real API, a spent daily limit answered "wait 26755 s", which ends at 00:00 UTC (5:30 AM in India), so that is what she says; the earlier assumption that it resets at midnight Pacific was wrong for this API and is gone. A per-minute limit is told as the wait Google named ("try again in about 40 seconds"); when Google names no wait she says both ("try again in about a minute — and if it still says this, it's the daily limit, around 5:30 AM"); Talk mode says the same for its own limit. When some models are out for the day but others only need a moment, she reports the soonest any model is back rather than the first model's failure. This is now honest for `web_search` and `analyze_document` specifically too, not just the main conversation; a real gap found live, where both had their own generic "search failed"/"could not read that file" wording that swallowed the actual reason, leaving the model to improvise something vaguer ("I'm still having trouble...") instead of the real, actionable message. Typed and spoken local commands keep working regardless, and the offline voice takes over.

Eya spreads load across models (limits are per model), retries "high demand" errors after a short wait, and stops asking a model whose daily quota is spent. Turning on billing for the project in Google AI Studio removes the practical limit.

**Search has its own, much smaller allowance — and doesn't stop Eya any more.** Gemini's Google-grounded search (what `web_search` uses) is metered separately from ordinary model calls. Measured directly on the free tier: with it spent, plain calls return 200 on every model while every grounded call returns 429 — so Eya looks "mostly working" but can't look anything up. When that happens `web_search` now quietly falls back to reading a real search-results page (DuckDuckGo first, Bing as backup) — in a throwaway background tab of your own connected browser that never disturbs the page you have open, or, with none connected, in a hidden lookup browser that only ever reads search results and never acts on a site and returns the top links — real addresses decoded from the engine's redirects, not guesses. The model then picks the link whose own domain is the organization's genuine site and opens that exact URL. This replaced an earlier prompt-only fallback ("open it from memory if you're confident"), which the Talk-mode model politely ignored in favour of asking you — a prompt can't fix a dead tool. Verified live with the quota still spent: "Open the Telangana High Court website" searched, found `tshc.gov.in` in the results, opened it and said "Done." in about 25 seconds; Talk mode's own tool path ran the same search in 6.6 s (its limit is 40 s).

Where the quota goes:

- Local speech recognition means spoken commands no longer cost a request.
- Talk mode uses the Live API, which has its own quota and kept working in testing when the regular one was exhausted.
- `analyze_document`, `web_search`, the typed/agent path and the cloud voice use the regular quota.

### Running out after four or five commands: what was done about it (10 Oct 2026)

A free Gemini key ran out of its day after four or five commands. Two things were behind it: every model step carried **all 85 tools and the whole 36 000-character instruction text** (about 25 000 tokens a step), and one command takes several steps. And when the key is out, nothing else can answer. Both are addressed:

- **Each request carries only what it is about.** The tools and the instruction text are in groups (core, browser, chat, Word, files, system, screen, memory); the core is always sent and the rest only when the words of the request point at them (`agent/toolGroups.ts`). Measured in the real app: an everyday request sends 21 tools and about 8 000 characters of instructions instead of 85 and 36 000 — a request body of about 22 000 characters instead of 105 000, **about a fifth**; a Word request 28 tools and about 41 000. The model is told what is switched off and can switch a group on with `load_tools` (instant, free); if it says "I can't" while abilities are off, Eya switches everything on and asks once more. Talk mode (the live voice) still sends everything.
- **Backup AIs (as many as six).** Settings → **Backup AI** lists them and adds more: pick a service, paste its key, **Save**. The services on offer (their addresses were checked to exist): Mistral, Cerebras, Google AI Studio (a *second Gemini key* from another account has its own free allowance), OpenRouter, Groq, SambaNova, NVIDIA, Hugging Face, Together AI, DeepSeek, xAI, Fireworks, OpenAI, and **Another service** for any address that speaks the OpenAI chat format (including a program on this PC such as LM Studio or Ollama, which needs no key). A key that starts `sk-or-`, `gsk_`, `csk-`, `hf_`, `nvapi-`, `xai-`, `fw_` or `AIza` selects its own service. Eya checks each key with its service before saving (and sends every key one tiny test message with the model she would use, so a wrong key, or a model the key may not use, is caught when you add it and not on the day Gemini runs out), saves it encrypted by Windows, and uses it **at once, no restart**. They are asked in the order listed, after Gemini: when Gemini is out, the first backup; when that is out too, the next; and so on, going back to Gemini when it returns. Choosing a model in the picker moves that backup to the front. Each service's other preferred models are kept as choices and as fallbacks; for OpenRouter that is every free model that can use tools. **Test** (18 Oct 2026): each backup in the list has a **Test** button that sends it a real test message and says plainly whether it works, whether its key is refused ("paste a new key below"), or whether none of its models answers; a model the key may not use is passed over and the one that works is put first. The list also says when the last real request found a key refused, an allowance over, or a backup resting. **A 403 from one model no longer stops the whole backup:** OpenRouter answers 403 for a model that is "only available on agentic harnesses" while its other free models work; before, that one answer made Eya treat the whole OpenRouter key as bad for ten minutes and skip it, so the switch-over from Gemini failed (found on the real keys). Now one 403 moves on to the next model (that model is left alone for half an hour), five models are tried per request instead of three, and only a 401, or two 403s in a row, is taken to be the key.
- **No waiting on a spent AI.** A provider that failed because its allowance is spent is left alone (30 minutes for a daily cap, a minute for a short limit, the service's own wait when it names one) and the next requests go straight to the next provider; while a backup is ready Gemini is told to give up quickly (two models, ten seconds, no retry rounds). The rests are remembered across restarts (`ai-state.json` in Eya's data folder; no secrets in it) and reset with the new UTC day.
- **You can see how far you got.** Settings → Backup AI shows today's requests per AI and how many each had answered when its allowance ran out. Gemini's answers also log their token count.
- **The truth when everything is out.** "Gemini and Mistral have both used up their free allowance for today… it comes back around 5:30 AM. Everything that does not need an AI still works: opening apps, files, folders and websites, searching, downloads, Word commands like page numbers and the running index, and messaging by name."

**What this cannot do.** A free key is still a free key: the allowance is Google's (and the backup's), counted per day, and the figures published for free tiers change and disagree between sources (Groq's free daily allowance, for example, is counted in tokens and is small). Eya cannot make a free allowance larger. The real fixes are, in order: a backup key from a service with a generous free plan (Mistral or Cerebras fit Eya best), turning on billing for the Gemini project (the diet above also makes each request cost a fraction of what it did), or both. The commands that never use an AI at all (see *Fast everyday commands*) cost nothing whichever way you go.

Environment (for running from source): `EYA_BACKUP_AI_KEY`, `EYA_BACKUP_AI_PROVIDER` (mistral | cerebras | groq | openrouter | openai | custom), `EYA_BACKUP_AI_MODEL`, `EYA_BACKUP_AI_URL`.

## Always-on listening: what to know

- Utterances over 10 s are dropped unsent; live speech over 14 words, or that sounds like conversation ("I'm going to show you…"), is ignored without any AI call.
- In always-on mode Eya only acts on commands; she never chats back at speech that wasn't one.
- By default Interrupt is on: in Talk mode the microphone stays open while Eya speaks, and Gemini stops her the moment it hears you talk over her. This relies on your microphone's own echo cancellation not picking up her voice from your speakers; if she keeps interrupting herself, turn Interrupt off, which goes back to muting the microphone while she talks (and for a moment after).
- The wake word is heard two ways at once: an on-device acoustic model (see above) and the existing check for the name "Eya" in whatever Whisper transcribes (however it spells it: "Aya", "I-A", "ee-ya" ...). Either can open Talk mode. A command-shaped phrase near the mic (TV, a call) could still trigger an action.

### The wake-word model, measured

Tuned and tested against synthetic speech (two Windows voices, three speaking rates) since this is a solo project without a speech lab: 60 recordings of "hey Eya" and its common mishearings, 182 short unrelated sentences, and about an hour of narration read from open-source READMEs as negatives.

- Offline, one clip at a time: caught about 8 in 10 attempts; 3 false alarms in 182 sentences (all on the phrase "hi Eya"), 0 in the hour of narration.
- Streamed live through the running app the way a real microphone would (one continuous, long-lived listener, exactly as it runs in production): caught roughly half of the attempts in spot checks, and still 0 false alarms in over 5 minutes of continuous narration. The lower number in continuous use looks like carried-over decoder state between phrases rather than a flaw in a specific clip; it has not been tuned further.
- This is why it is additive rather than a replacement: whatever it misses, the existing transcription-based check usually catches a moment later.
- Never tested against a real human voice or accent, so your own results may differ in either direction.

## A note on latency for the Windows-control tools

`close_file`, the volume tools and the brightness tools each shell out to PowerShell, and the volume ones compile a small C# COM-interop helper on every single call (PowerShell can't call a non-`IDispatch` COM interface like Windows' own volume API directly) — measured live at roughly 0.6-3.2 seconds per call, noticeably slower than the in-process file tools. This is a real, known cost, not a bug; a future pass could keep one PowerShell process warm instead of starting a fresh one each time, but that adds real complexity for what is a background system tweak, not the main flow, so it hasn't been done.

## How "ask before deleting" actually works

There's no separate pause-and-wait mechanism bolted onto the agent loop — it rides the same tool-call loop everything else already uses. A destructive or overwriting tool, called without `confirm: true` (or, for delete specifically, without `mode`), does nothing and returns a normal (if unsuccessful) tool result whose `data` is a small structured question (`{ status: 'permission_required', action, target, reason, options }`). The model is told, in that tool's own description and in the system prompt, to relay that question and only call the same tool again — with `confirm: true`, or with `mode: 'recycle' | 'permanent'` for a delete — once the user has clearly answered in that conversation. This means it works identically for typed commands, voice commands, and Talk mode, with no extra plumbing in any of them — verified live: asking to delete a file gets a spoken question offering both kinds and the file is untouched; a separate follow-up like "normal delete" or "permanently delete it, delete it completely" correctly re-targets the same file with the right mode (confirmed both by the reply and by checking the real Recycle Bin's contents), with no file path in the follow-up's own words at all.

## Reporting when something is actually done

Once a tool result confirms a plain action (open/close something, create/copy/move/rename/delete a file or folder, change a setting) truly succeeded, with nothing else worth mentioning, Eya's whole reply is just "Done." — not a description of what she did. She only says more when there's something to actually hear: an answer, search results, a caveat (an alternative was used, something was already in the state asked for, it stayed open), or a question of her own. This governs both the fast local path for simple app open/close (`ResponseComposer`) and everything that goes through the Gemini agent loop (a system-prompt rule) — verified live for both: opening Notepad, creating a folder, and completing a chosen delete all replied with exactly "Done."

## How the whole-PC file search works

`find_file`, with no folder named, runs two searches at once rather than stopping at the first one that turns up something:

1. **Windows' own file index** (`Search.CollatorDSO`, the same index behind Explorer's own search box and Start menu search) — instant, but normally only covers what Windows indexes by default, which is your own user profile, not other drives.
2. **A real filesystem walk of every other connected drive** (discovered live every time — never hard-coded to C or D), skipping Windows/program internals (`Windows`, `Program Files`, `Program Files (x86)`, `ProgramData`, `$Recycle.Bin`, `System Volume Information`, ...) and any other Windows account's own profile folder, but reaching ordinary user-created folders anywhere else.

If the index came back with nothing at all for that search, your own user folder gets a real walk too, concurrently — so a stale or disabled index, or a file that simply isn't indexed yet, doesn't produce a false "I couldn't find it". The two (or three) results are merged and de-duplicated before anything is shown. This was verified against a real second drive the index doesn't cover: a file that exists in three places at once (two indexed, one not) came back with all three, not just the indexed two — an actual bug, caught live, from an earlier version that trusted the index alone and stopped there whenever it found anything.

## How opening any installed application works

Beyond the short built-in list, `open_application` looks a name up against `Get-StartApps` — the same catalog Windows' own Start Menu search uses, covering ordinary Win32 programs and Microsoft Store/UWP apps uniformly. A match is launched via `explorer.exe shell:AppsFolder\<AppID>`, the one launch mechanism that works for both kinds (verified live against a classic `.exe`-backed entry and a UWP AppUserModelID-backed one). Since a dynamically-discovered app's eventual process name isn't known in advance, it's verified by snapshotting running processes just before launching and confirming a genuinely new one appears afterward — verified live launching Visual Studio Code (not on the built-in list) this way. Entries Windows itself also lists there but that are never really "the app" — an uninstaller, a documentation or website shortcut — are filtered out by name before matching, so "open node" can't be misread as "run the Node.js uninstaller".

If nothing is genuinely installed, a small table of apps with a real official web client (WhatsApp, Telegram, Discord, Spotify) is tried instead, opened in whichever browser already has several processes running — a rough but effective "is this one actually open, not just a leftover background helper" check — or the default browser otherwise. Verified live: WhatsApp (not installed on this machine) correctly opened `web.whatsapp.com`. Tab awareness in your everyday browser used to be impossible for Eya (attaching to an already-running browser isn't something Windows lets another program do after the fact); it now exists for website tasks through the Eya Browser Bridge extension (below), which can see your tabs and reuse the one you already have open. `open_application`'s own web fallback is unchanged: it just opens the address, which Windows' single-instance browser behaviour usually lands as a new tab in the browser already running.

## How website navigation works

The core rule: "go to Cause List" means look at the page that's actually open and click the real thing, never turn it into a web search or invent a URL. `open_website` opens a page in your own Chrome or Edge, through the extension (see "Using your own signed-in browser" — it used to open a separate Eya window, which started signed out; that is no longer the default and never a quiet fallback); `inspect_page` reads what's genuinely on it (headings, visible links, buttons, form fields); `click_on_page`/`fill_on_page` act on something from that real, freshly-read list by its visible text or label. The model is told explicitly, in both the system prompt and each tool's own description, that `web_search`/`open_url` are for finding a site or showing a one-off page, never for moving around inside a site that's already open.

A real bug surfaced live while building this, worth recording: a link or button's visible text, read straight from the page, often comes padded with the surrounding markup's whitespace (`"\n\t\t\t\tCause List\n\t\t\t"`), and re-querying Playwright for "the element named exactly that text" doesn't reliably match what the browser itself computes as that element's accessible name — on the real High Court of Telangana site, this made a click silently hang for 40 seconds before failing, for a link that was genuinely right there. Fixed by never re-querying by name at all: the matching logic picks an *index* into the same list of elements it just read, and clicks that exact element directly, so the two systems never need to agree on what counts as "the same name". Verified live end-to-end, with that exact fix, against two unrelated real sites: opening the High Court of Telangana's site, clicking "Cause List" then "Entire Causelist" (which genuinely reached a results page, not a guess), and separately opening Wikipedia and clicking "Donate" — proving it's a general mechanism, not something tuned to one page.

**Nothing about any specific website is ever predicted.** Every `open_website`/`click_on_page`/`fill_on_page` result carries a completely fresh read of whatever page it left the browser on — its own headings, links, buttons, fields and any visible popup/dialog — and the system prompt is explicit that this fresh result, not a remembered structure or a convenient example, is the only thing the next decision is based on. A native `alert()`/`confirm()`/`prompt()` popup (which would otherwise block the whole browser, waiting forever) is auto-dismissed and reported in the very next result instead of silently hanging. This was a real course-correction: an earlier version of the system prompt illustrated "ask the user to choose" with the Telangana cause list's own category names as an example, which risked the model treating one site's structure as a pattern to expect elsewhere — removed, with the rule now stated only in the fully generic form (if the live page offers a genuine choice the user's own request doesn't already resolve, list the real options it actually shows and ask; if the request already determines the choice, or there's only one sensible option, just act). The agent's own step budget was raised (8 → 16 tool calls, same 90-second ceiling) since a real multi-page task can need more round trips than a file search ever did.

**Loop protection.** `click_on_page` and `fill_on_page` remember what they just tried: the same action on the same target, from a page that looks exactly the same (a fingerprint of the address, title, and everything visible — so a menu opening in place counts as a change even though the URL doesn't move), is allowed twice and refused the third time without touching the browser. The refusal hands back the live page and says plainly to pick a genuinely different action or ask you, so the model changes strategy instead of spinning. It also catches a bounce — click A, land on B, come back, click A again — because the page state repeats. Typing a different value into a field, clicking something else, or the page actually changing all count as new attempts, so paging through results with "Next" is never blocked; attempts older than two minutes are forgotten so asking again later is a fresh try. Results also now say `stateChanged` (anything visible differs) separately from `navigated` (the address moved), so "a menu expanded" is distinguishable from "nothing happened" and from "went to another page". Verified live against a local page whose "Check status" button never changes anything: the first two clicks ran, the third, fifth and seventh attempts were refused in ~26 ms each (including after the model tried reopening the page as a fresh start), and Eya reported honestly after 8 steps instead of clicking until the step limit.

Deliberately not built, because each needs its own real testing as a separate subsystem: a Gemini Computer Use (screenshot-driven) fallback for when DOM inspection alone can't identify something, and Windows UI Automation as an alternative path. (Downloading and verifying a file a site produces now exists when working in your own browser — see below.) Loop protection covers website clicks and form fills; it does not (yet) watch other tools for repeated identical calls.

## Why she used to get "stuck on the main page" (fixed)

Reported: on any site Eya opened the main page and clicked something it showed, but the options *after* that click were never found. Reproduced on real sites before changing anything; there were four separate causes, not one:

1. **The page's real options never reached her.** She was shown only the first 40 links in page order, and a site's menu bar, repeated on every page, fills that list — so on the next page the options that mattered were cut off. Now the page's own links (up to 80) are listed apart from the site's menu bar / header / footer (found by landmarks, and by class names for sites that have none), and a menu bar identical to the previous page's isn't repeated at all.
2. **Hover menus were invisible.** A dropdown that only opens on mouse-over (pure CSS `:hover`, which no script can trigger) held links she could not see. Those links are real parts of the page, so they're now listed under the menu that holds them and can be clicked by name directly.
3. **She couldn't read, or search, a page.** New `find_on_page` (searches everything: showing, further down, closed menus, the page's text) and `read_page` (the page's text, slice by slice). The system prompt now says a successful click is one step, not the end: keep going level by level, and use these before concluding an option doesn't exist.
4. **Wrong element on shopping-style search boxes.** Playwright's label lookup matched Flipkart's search *button* (it carries the same label as the input) and tried to type into it. Eya's own window now runs the identical page script as the browser extension instead of a second, separately written implementation — so a fix in one is a fix in both.

Also: a long product name shown shortened with "…" could not be clicked by the model quoting it (exact match failed); matching now tolerates a name cut short at either end. And when a tool fails, the agent log now says why instead of only `ok: false`.

Checked on real, public sites through the real agent (read-only): the Telangana High Court site (a hover-menu item, "Entire Causelist", clicked straight from the main page, and the form read), Flipkart and Amazon (search → first result → price), Wikipedia (read the population from the page), India.gov.in (service categories, then a category two levels in), BBC Sport, GitHub Explore, YouTube search. (Those runs used Eya's own window; that window is now opt-in only — see the next section.)

**What this does not do, deliberately:** get past a CAPTCHA, a "verify you are human" check or any other bot detection. Eya stops there and asks you to do that part, then carries on. The honest way to see fewer of them is the Eya Browser Bridge below: your own, already-signed-in browser looks like what it is.

## Why websites showed a signed-out session (fixed)

Reported: every site Eya opened looked like a brand-new visitor, even though the user was signed in in their own Chrome/Edge. Audited in code rather than guessed at:

- **The cause.** `open_website` went through `SwitchingBrowserService` (`browserRouter.ts`), whose default mode was `auto`: your own browser if the extension happened to be connected *at that moment*, otherwise Eya's own `PlaywrightBrowserService` window (its own empty `browser-profile`, wired up in `src/main/main.ts`). A browser that had not paired yet, had been updated, or had just dropped off the bridge therefore produced a fresh, signed-out window, with only a line in the result saying so.
- **A second flaw next to it.** The bridge held exactly *one* browser connection: connect Edge while Chrome was paired and Chrome was evicted, and the single shared secret meant the two fought each other.
- **The fix.** The default is now `user_browser`, and the fallback is gone from the code path rather than discouraged in a prompt: `BrowserSessionManager` has no route from "your browser isn't available" to "open a separate one" unless the call says `isolated: true` (the prompt only allows that after you agreed) or you set `EYA_BROWSER_MODE=eya_browser` / `auto` yourself. When your browser can't be used, the tool result carries `data.why` (`needs_pairing`, `not_connected`, `no_extension`, `no_browser`, `lost_connection`) and Eya tells you the one thing to do. A browser that drops out *mid-task* stops the task ("instead of carrying on in a different browser") rather than moving it.
- **An out-of-date extension is named for what it is.** After updating Eya, the extension still running in a browser is the old version until it is reloaded, and Eya refuses it. The bridge remembers that refusal, so the result says "the extension in Edge is the old version — reload it at edge://extensions" (`data.why: needs_reload`), never the vague "check it's switched on" and never "install it again"; `browser_status` shows it too. If another of *your own* browsers is already paired and healthy, the site opens there instead (starting it with your normal profile if it is closed) and the result says so — still never a separate automation window.
- **Chrome and Edge side by side.** One connection and one stored secret per browser; one pairing window pairs both. Each browser's tabs, windows and state are tracked separately.
- **Which browser, which tab.** Policy in `browserSelection.ts`, in priority order: a tab already open on the site (an exact address first; if both browsers have one, the browser you are in front of, then the one this task has been using) → the browser this task is already in → the browser you are in now → your preferred browser → any connected one. Then, inside that browser: reuse the matching tab, else open a new tab in the *same* browser, else (nothing running) start your normal browser with the address (`browserLauncher.ts`) and wait for its extension — never an automation profile.
- **Sign-in, CAPTCHAs, codes.** Eya stops, tells you in one sentence what the page wants, and calls `wait_for_user_in_browser`, which returns as soon as you act (or after 30 s, then again). When it reports you are done she carries on with your *original* request without being asked again. Eya never types a password or code and never reads one.
- **Interruptions.** The extension tags every tab/window/download event as "Eya" or "you". If you changed something between Eya's steps, the next result carries a note and Eya reads the live page instead of trusting her picture.
- **What was *not* built, by design:** no cookie copying, no fingerprint or `navigator.webdriver` changes, no CAPTCHA or bot-check handling, no proxy tricks, no unauthenticated local endpoint. The extension asks for no `cookies`, `webRequest`, `history` or `debugger` permission, and tests pin that.

## Using your own signed-in browser (the Eya Browser Bridge)

Eya's own browser window starts signed out of everything, which is useless for "check my orders" or "what's in my inbox". The Eya Browser Bridge (`eya-chrome-extension/`) lets her use the Edge or Chrome you are already signed in to. Its own README lists the permissions and limits; the short version:

**How it's wired.** The extension (Manifest V3, plain JS, no build step) dials `ws://127.0.0.1:47821/eya-bridge` on this PC and nothing else. Eya's `ChromeBridge` accepts a handshake only if its `Origin` is exactly the extension's (the ID is fixed by a public `key` in the manifest and a test keeps the two in sync — a web page can't forge that header), and, after a one-time pairing that *you* start by saying "connect my browser" (a two-minute window that pairs each browser once, so Chrome and Edge can both be done together), only a connection presenting the secret it was handed then. Eya stores only a hash of each browser's secret. Each connection opens with a versioned handshake (browser, version, extension version, capabilities, windows, tabs, active tab); an extension on another protocol version or lacking an ability Eya needs is refused with a plain "reload the extension" message, and a stopped bridge never carries an open pairing window into its next start. After that the extension streams live events (tabs created/closed/activated/updated, navigations, window focus, downloads), each marked as Eya's or yours, which Eya folds into her picture of each browser. `ChromeBrowserService` sits behind the same `open_website` / `inspect_page` / `click_on_page` / `fill_on_page` tools as before, so loop protection, confirmation gates, the search fallback and the prompts all apply unchanged; `BrowserSessionManager` decides which browser a task uses.

**Every action is look → choose → act → look again.** The service asks the page what is there (links, buttons, fields, drop-downs, checkboxes, same-site frames, shadow DOM, things that merely *look* clickable), picks an element that really exists by its visible text, acts, waits until the page has finished loading *and* stopped changing (including pages that go quiet while still showing "Loading…"), follows it if it opened a new tab or started a download, then looks again. The result carries what appeared and disappeared, popups, a new tab, and a download that is only reported — with its path, so "open it" works — once the file is verified on disk. Elements are checked just before the click: if the page changed under it ("stale"), Eya looks again and re-chooses once; if something is covering the control (a cookie banner) she is told what.

**Hard rules, enforced in code rather than in a prompt:** CAPTCHAs and bot checks are noticed and Eya stops — no clicking around them, no solving, no retrying — and asks you; a page asking for a verification code is noticed, the task is kept, and she asks you to say the code (see "Waiting for a verification code"); passwords and card numbers are never typed, and no field's value is ever read back (the page script refuses; the desktop side refuses again independently); a click on something that would buy, send, delete or change an account setting returns a question and does nothing until your yes; query strings and fragments that look like credentials are stripped from every address she's shown; no cookies, storage or history permissions exist at all; and she never navigates a tab you were using — she reuses tabs *she* opened, and only brings a matching tab of yours to the front.

**Measured, in both Chrome (154) and Edge (154), with the real extension, a real bridge and local sites built from page structures the code was never written for** (a hidden hamburger menu with a nested submenu, a cookie overlay covering the page, shadow DOM, a same-site iframe, a page that fills in after a second, a CAPTCHA-style page, a download, a link opening a new tab — and, added after the "stuck on the main page" report, a portal with a 64-link header on every page and a pure-CSS hover dropdown): 26 live tests for the extension and 12 for Eya's own window per browser, in `tests/live/` (opt-in: `EYA_LIVE_BROWSER=1 npx vitest run tests/live`; Chrome by default, `EYA_LIVE_EXE=edge EYA_LIVE_CHANNEL=msedge` for Edge; headless, temporary profile, never touches your own browser), plus a 24-check end-to-end run through the real running app and its real tool registry (`node tests/live/e2e-real-app.mjs`, how to run it is at the top of the file) — pairing from `connect_chrome`, discovering the menu live, form fill and Enter-submit, the confirm gate, password refusal, CAPTCHA stop, a verified download, listing and switching tabs, killing the browser mid-task (Eya stopped with "browser not connected" and did **not** open a substitute window), and the browser coming back by itself about a second after a restart using the stored pairing. A web page trying to open its own socket to the bridge was refused in a real browser.

**Things found only by running it, and fixed:** the browser's own "Back" button skips pages that never received a real user gesture, which includes every page Eya reached with a script-made click, so `go_back` now uses the page's `history.back()`; a label wrapping a `<select>` swallowed every option into the field's name; and Edge disables an *unpacked* extension at its next restart when Developer mode is off (measured: enabled → disabled with reason `unsupportedDeveloperExtension`; with Developer mode on, it survives a hard kill and reconnects in about a second) — which is why the setup steps say to turn Developer mode on and leave it on.

**Honest limits.** Chrome 137 and later ignore `--load-extension`, so there is no silent way to put the extension into your Chrome: it is the one-time "Load unpacked" click (the tests load it through Chrome's debugging protocol instead, and Chrome forgets a protocol-loaded extension at restart, whereas a real Load unpacked is remembered — that persistence I could only measure in Edge, where leaving Developer mode off made the browser disable the extension at its next restart; keep Developer mode on in Chrome too). Eya's clicks are script-made events, so a page that needs a *real* click to open a script popup (`window.open`), a file picker, fullscreen or the clipboard will not respond (pinned by a test so it's never forgotten; trusted clicks would need the `debugger` permission, which the extension declines). Controls inside another site's iframe can't be seen into. Browser-internal pages can't be read. Everything above ran against a temporary empty profile and local sites, plus read-only visits to a handful of real public sites through Eya's own window: **your own signed-in accounts, real MFA flows and the quirks of sites that sign you in have not been tested** — that needs your one-time install and a try.

## Communication Access (chat apps are off until you switch them on)

Eya can work inside chat apps and sites — WhatsApp, Telegram, Instagram, Messenger, Discord, Slack, Teams, Skype, Signal — but only
if **you** allow it. The **Chats ON/OFF** pill in her panel opens the switch, with a plain explanation and a per-app list. It starts
**OFF**, it is saved on this PC, it never turns itself on, and **Eya cannot turn it on** (no tool does; asking her in a chat, or a
web page or message telling her to, changes nothing).

- **While it is OFF** she does not read a chat page, click or type in one, take a picture of one, read its tab title (a contact's name)
  or search contacts. Opening the chat for you is fine; what she gets back is only that it is open. This is enforced in two places:
  in Eya, and in the browser extension (which declines to use its access for those sites — a browser lets an extension read every
  site or none, so declining is the most it can do). E-mail is deliberately not a "chat app" here.
- **When it is ON** (all apps, or all but the ones you untick) she works in them with the same general browser tools as anywhere else.
  Even then, a chat's tab title and address reach the model only as the app's name, and the instructions tell her never to repeat
  private messages or save them anywhere.
- Nothing from a chat is stored by Eya, with one exception that is **off until you say yes**: the *names* of chats, so she can find
  one quickly (see "Messaging by name, and the chat names Eya remembers" below — names only, never a message, a preview or a number,
  all listed on the Memory screen, and erased the moment you turn Chats off for that app). Otherwise the only thing written to disk
  is the switch itself (`communication-access.json` in her data folder). A damaged or unreadable file means OFF.
- Turn it off at any time; it takes effect on her very next step, even in the middle of a task.

## Sending a file or a message in a chat app

With Communication Access on, "send the folder Hello 2 on my desktop to the Uber chat on WhatsApp" is a handful of small, general steps — **observe, act, observe, verify** — over the same browser tools as everywhere else, in the browser you are already signed in to. Nothing is written per app; what differs between WhatsApp, Telegram and Instagram lives in their own pages.

1. Open the app in your browser (`open_website`, in the browser you name).
2. `find_chat` — the name or digits you gave; asks you which one if two fit.
3. A folder → `find_folder`, then `zip_folder` (she says she is sending a zip). A file → the exact path from `find_file` (searches the whole PC) or from earlier in the conversation.
4. `attach_file` → she asks *"Found <name>, number ending in …. Send the file … to this chat?"* and waits for your yes.
5. Send (the yes covers exactly that file and that chat, once) → `verify_sent`. She says "sent" only when the app itself shows a new delivery mark; otherwise she tells you what she saw.

A typed message asks the same way before Send. Backing out of a preview withdraws the yes, and a yes runs out after a few minutes.

**Tested for real** with the actual extension in a real Chrome, through the real tools, against two chat pages built nothing alike (a WhatsApp-style and a Telegram-style one): ambiguity, number search, byte-exact transfer of a 7 MB file in several parts (SHA-256 compared in the page), no-picker-until-the-attach-menu, a preview with a second "Send", a send the app reports as failed, a zipped folder, and everything refused when the switch is off. **Not** tested: the real WhatsApp, Telegram or Instagram sites (they need your signed-in account and phone, and change their pages without notice). The extension is where that will show first; if one of them behaves differently, the result says what it saw instead of claiming success.

## Messaging by name, and the chat names Eya remembers

"Message Ravi that I'll be late", "send good morning to Amma on WhatsApp", "tell Priya I reached", "open Sita's chat", "message Rahul Sharma: running 10 minutes late" — each runs **without the model** (`src/main/local/ChatCommands.ts`): the same chat tools, in a fixed order, under the same rules. She finds the chat, types the message into its box (**not sent**), and asks *"Found Rahul Sharma, number ending in 432. Send "I'll be late"?"*. Only your own clear yes presses Send — then she checks the app really shows it went and says "Sent to Rahul Sharma" only if it does (otherwise she says what she saw: failed, still sending, or can't confirm). The message goes out word for word as you said it. If two chats fit ("Rahul" → Rahul Sharma or Rahul Verma) she asks which — "the second one", "Verma" and "2" all work. Sending a **file** is a different job and still goes through the model and its own question ("send report.pdf to Ravi on WhatsApp").

**It never acts on always-on listening.** A message is only started, and a question only answered, by what you say or type *to Eya*; a "yes" heard from a room or a video is not a yes. An unanswered question lapses after two minutes. If your browser isn't connected to Eya, she hands the request to the model, which knows how to help connect it.

**The chat names (off until you say yes).** After the first message that really went, she asks once: *"I can remember the names in your WhatsApp so I find chats instantly next time — names only, kept on this PC, never messages. Want that?"*. You can also say **"remember my WhatsApp contacts"** (that is the yes; she reads the names showing in the chat list), **"how many contacts do you know"**, **"forget my contacts"** or **"stop remembering my contacts"**, or use the **Chat names** tab on the Memory screen (a tick box, every name listed with a × beside it, and "Forget all names"). What is kept: a chat's *name* as the app shows it, how often she opened it, and what you call it ("mom" for "Amma") once you have confirmed a send under that name. What is never kept: a message, a preview, a time, a phone number, a picture. Anything that doesn't read as a name (a sentence, a link, a number, a time, a button) is turned away; there is a limit of 2,000 per app. **The names of an app are erased when you turn Chats off for it** (and when Eya starts with it off), so a name list never outlives the switch; turning Chats back on starts again from nothing. Saying no keeps nothing, and she doesn't ask again. The names are never given to the model.

**What the names change — and what they cannot.** They turn "Priya Singh" or a name you've confirmed ("mom") into the exact chat before searching, work out where a name ends when you didn't say ("message Priya Singh I'll call tonight"), and ask which of two saved Ravis you mean at once. They never *narrow* a partial name: Eya only knows the names she has learned, not your whole address book, so "Rahul" matching one saved Rahul is still searched in the app, which sees everyone (a real bug caught while testing in Chrome). The names are also learned passively — the rows the app shows for a name you asked for, and each chat she opens — only after you've said yes.

**Speed — and what was really slow.** Resolving who you mean takes about 15 ms and no model call (it used to be several Gemini turns of 7–40 s each). The page steps were the other half, and the cause was not the chat logic. After *every* click and fill the browser extension (1) waited up to **2.2 s to see whether a download had started** — typing in a box cannot start one — and (2) waited for the page to go completely quiet (up to 2.5 s), which a chat page never does (presence, timestamps, typing marks), so each step always ran to its ceiling. Timed per bridge operation (`EYA_BRIDGE_TIMING=1` logs each one; reading the page costs 5–10 ms), then fixed:

| On the mock chat page, real Chrome + the real extension, this laptop | before | now |
|---|---|---|
| "message Rahul Sharma that …" → Eya asks "Send …?" | 8.9 s | **0.8 s** |
| your "yes" → sent and checked | 2.9 s | **0.6–1.1 s** |
| "send the latest pdf to Priya Singh" → Eya asks | (the model, several turns) | **0.8 s** |
| your "yes" → attached, sent and checked | (the model, several turns) | **1.6 s** |

How: the extension (**0.5.0**) has a *quick* mode for single-page apps — a short calm instead of a full quiet, and no wait for a download — and Eya turns it on only for chat pages (and typing or scrolling never waits for a download on any site now). `find_chat` reads the list every ~100 ms (10 ms each) until it has changed and stopped changing, instead of a fixed pause, and looks once more before saying "no such chat" because a search can be answered late; the "did it go?" check looks every 250 ms instead of 700 ms; opening WhatsApp when its tab is already open takes one short wait instead of 1.5 s. **Reload the extension once after updating** (the circular arrow on its card on the extensions page): until you do, everything works exactly as before but at the old speed, and Eya says so once after a chat step instead of leaving you to wonder. The mock page is much lighter than real WhatsApp Web, so expect real numbers to be higher; they are not measured on a real account.

**Sending a file by name** ("send the latest pdf to Akka", "share resume.pdf with Amma on WhatsApp", "send Ravi my passport scan") is a local command too: the file comes from the same in-memory index as "open the latest pdf", the chat is opened as above, and she asks once — *"Found Priya Singh, number ending in 432. Send the file "report.pdf"?"* Only your yes attaches anything: she then opens the app's attach menu if it keeps its file input hidden, attaches, presses Send and checks it really went. Several files that fit are named (say the exact name); a file she can't find quickly, a folder (zipped first) or a name she doesn't know without an app named ("send the report to my boss" may be an e-mail) is left to the model.

**The extension pairs itself (extension 0.6.0) — nobody has to say "connect my browser".** Loading the extension is the only step. Eya leaves a key in the extension's own folder (`eya-chrome-extension/eya-pairing.json`, made at her first start, git-ignored and left out of the installer); an extension that has no pairing secret yet reads that key and presents it, and Eya hands it its own secret straight away. The same thing quietly repairs a reinstalled extension, a secret Eya no longer knows, and "forget my browsers". What the key does and does not allow: a web page or another extension cannot read that file (it is not web-accessible, and the connection must also come from this extension's own origin); only something that can read the folder as you can has it — the same people who could read the extension's own stored secret anyway. A second profile of a browser that is already connected cannot take its pairing away (it waits until the first is gone). If the folder cannot be written (a read-only install) or the extension is older than 0.6.0, the old way still works: say "connect my browser" and Eya opens a short pairing window. Measured in a real Chrome (`tests/live/autopair.live.test.ts`): paired within a second of Eya starting with no window opened, reconnected after an Eya restart without pairing again, paired again by itself after "forget", and the extension's Errors list stayed at 0 even with no key file. Reload the extension once to get 0.6.0.

**Which browser: Chrome, unless you name another.** Anything Eya opens or works in goes to Chrome. Say "in Edge" (or "on Firefox" for a plain page) and that browser is used instead, for that request. This used to follow "wherever the site is already open" and "the browser you were last in", which could quietly pick Edge; it no longer does, and when Chrome's extension needs a reload or pairing Eya says so rather than using Edge. Chrome is started (your normal profile) if it is closed. Only a PC without Chrome falls back to Edge. `EYA_PREFERRED_BROWSER=edge` makes Edge the standard instead. A task that is already running in a named browser stays in it; the next page you don't place goes to Chrome. Where: `browserSelection.ts` (`defaultBrowser`), `BrowserSessionManager.resolveForOpen`, `open_url` / `open_application`'s web fallback, and `localIntents.ts` for the spoken "… in Edge".

**The extension's "Errors" list (fixed in extension 0.5.1).** The only thing it ever logged was one failed-connection line per attempt while Eya was not running, a few per minute, all day. It now looks for Eya with a quiet web request first and connects only when she answers: 0 errors with Eya off or restarting, measured in a real Chrome. Reload the extension once, and press "Clear all" on its Errors page. (Details in `eya-chrome-extension/README.md`.)

**The "I can no longer see the file" loop (fixed).** In a live conversation, after the user's "yes" the file attached, and then Send was refused again and again with *"Found Uber. I can no longer see the file "…docx" waiting on the page. Send what is on the page to this chat?"* — however many times they said yes. Cause (found from the real log): the Send gate required the file's whole name to be written on the page, but WhatsApp's preview shows a long name cut short and without its extension, while the attach step had accepted the same preview; so the gate could never be satisfied. Now the gate (and the "did it go?" check) accept a name by its start (the first two words, five letters each, so a cut in the middle of a word is fine) and an open preview the attach step recognised; a preview that is really gone is still noticed, and the yes still covers only that chat and that file for three minutes. Reproduced first as a failing test (a fake chat app with `cut_name`, a mock page with `chat.html?cut=1`, and a real-Chrome run of the model's own steps), then fixed.

**Follow-ups and remembering.** "Send it to Uber", "send that file to Amma" and "send for Uber" use the file found last — by Eya's search, by the model in a live conversation (its results now go into the conversation too), or opened a moment ago — and a question and a command said together ("Uber chat is there na? Send for Uber.") are read as the command. With no app named, "send it to my boss" is left to the model (it may be an e-mail) unless a chat app is open or the name is a chat Eya knows. In a live conversation the model is now told that sending a file is a `quick_command` job (it used to be told to use `attach_file` itself, which is the slow, loop-prone path). And after *any* confirmed chat send — including one the model did step by step — a user who was never asked is asked once whether Eya may remember chat names (names only); remembering starts only with their yes.

**When the name you say is not the name WhatsApp shows** ("akka", "amma", "bhai"): say it once — *"when I say akka I mean Lakshmi Akka"*, or open the chat and say *"call this chat akka"* — and that word goes straight to that chat from then on (your asking is the yes to keeping it; names only; a word has one meaning, so giving it to another chat takes it from the first). Without that, three things help: the chat you message clearly most (opened at least 3 times, and 3× as often as any other that fits) is taken when several fit — she still says who she found before anything is sent; spellings that sound alike are the same name ("aka", "akka", "acca"; the speech recogniser spells names by ear), tried only when nothing matches better; and an exact name beats a longer one that merely contains it.

**Verified:** 36 unit tests against the chat tools and a fake chat app (including the "Rahul" bug, the "second one" reply, a send that fails, no message box, no browser, always-on listening ignored, unanswered questions lapsing), the parser (16 tests), the name store (21), the Memory screen's actions, and a live suite (`tests/live/chatcommands.live.test.ts`, 7 scenarios) in real Chrome with the real extension against a WhatsApp-style page; the Memory screen and erase-on-Chats-off were checked in the running app. **Not verified:** the real WhatsApp, Telegram, Instagram — they need your signed-in account, so the first real run is yours. If it learns something that isn't a name, remove it on the Memory screen and tell me.

## The bubble, the quick assistant and the Eya window

Eya is one window in three shapes, all the same page — so the microphone, the "Hey Eya" wake word and the live conversation are never duplicated or moved:

- **The bubble:** a small round orb, always on top, that you leave anywhere on the screen. It starts against the right edge, above the taskbar. **Drag** it and it follows the pointer, then settles against the nearer side edge; where you leave it is remembered (`window-state.json` in her data folder, next to `settings.json`). It shows a green dot while she is listening, an amber dot while Chats are ON, and a blue pulsing dot when she has a question for you ("save this as a routine?").
- **The quick assistant:** **click** the bubble (a press that moves more than a few pixels is a drag, not a click). A panel grows out of it — above a low bubble, below a high one, on whichever side has room; if the screen is short the panel is trimmed and scrolls, and the bubble **never moves** when it opens. With *Click the bubble to talk* on (the default) the click also starts a live conversation, like tapping a phone assistant, and clicking again stops it. Esc (when you are not typing in a box), ✕, or Ctrl+Space puts it away; ⤢ opens the full window.
- **The Eya window** (⤢, a click on the tray icon, or starting Eya a second time): a sidebar with **Home** (her face, a box to ask her anything, quick doors, what she did lately), **Chat** (the conversation, typed, spoken and live, in one place — kept in memory only while the app is open), **Live Screen**, **Files**, **Recent**, **Memory** and **Settings**. Closing or minimising puts her away as a bubble; she keeps running and listening. **Quit Eya** is in Settings → About and the tray menu.
- **Right-click the bubble, or the tray icon:** Open Eya · Ask Eya · *Chats: ON — turn off* (or *Chats: OFF — set up in Settings…*) · Show the floating bubble · Start with Windows (installed app only — from source it would register a bare Electron, so it is switched off) · Quit Eya. Chats can be turned **off** in one click from here, but only **on** from Settings, where what it allows is explained and you confirm.

**Chats ON/OFF** is in four places now, all the user's own controls (no voice command or tool can reach them): the Chats pill in the quick panel, Settings → Privacy & Chats, the sidebar pill, and the bubble/tray menu.

**Recent** keeps a short list of what Eya did — a title and one line of outcome, with a **Repeat** button — in the same SQLite database (`activity` table, schema version 2, migrated in place). Nothing from a chat app is listed (just "Worked in a chat app", not who or what), a request that looks private (a password, a long number, an e-mail address) shows only as "A private request" and cannot be repeated, and talk about memory or settings is not listed at all. It keeps the latest 300 entries for up to 90 days, and Settings → Privacy can switch it off or clear it. The sites she opens most feed *Frequently used websites* on the Memory screen.

**Verified in the running app** (real Electron, a real display at 125% scaling): first-run placement; click versus drag; a **real cursor drag** (the OS pointer moved, the bubble followed, settled on the left edge, saved its place, and was there after a restart); opening and closing the panel repeatedly from a high-left bubble without the bubble drifting (a drift bug found and fixed this way); every screen with real data; Chats ON/OFF; hiding and restoring the bubble; the close button putting her away without quitting. Placement rules are unit-tested across four screen shapes. **Not verified:** the tray icon's appearance and menu clicks (the menu's logic is unit-tested, the icon is drawn in code and creates without error), the installed app and Start with Windows, and other DPI scalings or multi-monitor layouts beyond the geometry tests.

## Fast everyday commands (no model, no internet)

The things people ask for all day are fixed shapes, so Eya recognises them herself instead of sending them to Gemini (seconds, and the internet) — `src/main/local/`:

| Say | What happens | Measured here |
|---|---|---|
| "open YouTube" / "go to github dot com" / "open https://…" | the site opens in your default browser (about 35 well-known sites, or any web address) | 70–90 ms |
| "search Amazon for phone cases" / "google weather" / "look up ohm on Wikipedia" | the site's own search page opens (the words are URL-encoded; they cannot change the address) | 70–90 ms |
| "open downloads" / "open my documents folder" / "open the cases folder" | File Explorer opens on it (a folder by name comes from the index; two equally good ones are not guessed) | 1 ms to decide |
| "find my resume" / "show me my latest PDF" / "find the invoice pdf in downloads" / "my photos from today" | answered from memory: the best matches and which folder each is in | 1–9 ms |
| "open the invoice pdf" / "open the latest pdf in downloads" | opens the one file clearly meant; with several equally good matches she names them and asks "Which one?" | 130 ms (Notepad window up) |
| "open Paint" / "open Word" / "open Spotify" | any app in the Start Menu, by its exact name, without the model | the launch itself, 1.3 s (see below) |
| "download https://…" / "download this" (a link you copied) | saved to Downloads (see below) | 1.1 s for a 105 KB file |

**What makes it fast.** Two things are remembered in memory instead of asked of Windows every time: the **file index** (`FileIndex`: the *names*, sizes and dates of what is in your Desktop, Documents, Downloads, Pictures, Videos and Music folders, built in the background shortly after start-up and kept current by the file system's own change notifications, with a full re-read every 30 minutes as a safety net) and the **Start Menu app list** (`AppCatalog`: `Get-StartApps` took 1.2 s on this laptop, and "open Spotify" used to pay that every time). On this laptop's real folders the index is 4,514 files, builds in about 0.5 s without ever pausing the rest of the app for more than ~7 ms, uses about 8 MB, and a search takes 0.4–0.6 ms (the old way was a fresh PowerShell: 350–500 ms before it had looked at anything). It never holds file *contents*; it skips secrets (`.env`, keys, certificates), programs and scripts, `node_modules`, `.git`, hidden and protected folders, and never follows a junction or symlink.

**She only answers what she is sure of.** The words are matched by shape: she needs the verb *and* a concrete thing (a known site, a known folder, a file with a type or "my …"). "Find a good restaurant", "open the door", "search for cats" and anything vague go to Gemini exactly as before. If the file index has nothing (a file on another drive, a name she doesn't have yet, a file that has just gone), she hands the request on, so the whole-PC search below still runs: the index being incomplete only ever costs time, never a wrong "no such file". The order is: apps (instant shortcut) → your saved routines → these commands → Gemini; a routine you saved always wins, and none of it is taken from always-on listening beyond a short command (a download is never started from always-on listening at all).

**Short answers, because the ear is the slow part.** The decision takes milliseconds; reading the answer aloud takes seconds, and it was the longest wait on a file search (a reply that read out three full names, one a 15-digit scan number, ran about 15 s on the offline voice). A list of files is now read as briefly as it can be without losing what tells them apart: long digit strings are said as "a number", a name is cut after six words and lone dashes are dropped (the real path is kept, so "open the second one" still opens the right file), the folder is said once when they are all in it ("all in Downloads"), and the file type is left off when they are all the same (you asked for a pdf). "A word document" now means Word's own files (it used to search every kind of document for names containing "word"). Opening a file or folder, and everything else she says, is unchanged.

**Downloads** (`download_file`). The address must be http(s); a program or script (`.exe`, `.msi`, `.bat`, `.ps1`, `.js`, `.lnk`, …) is refused, by the address *and* by the name the server gives; an address on this computer or your local network is refused (including a redirect that ends up there); the name can never leave the Downloads folder; nothing is overwritten (a second copy becomes `name (1).pdf`); a half-arrived file is kept under a temporary name and only renamed when all of it is there; a stalled download is given up on after 30 s; the limit is 4 GB; and the finished file is marked as coming from the internet (the same `Zone.Identifier` a browser adds, verified on a real download) so Windows warns before anything inside it is run. When *you* say or paste the address, or copy a link and say "download this", that is your yes; when the model wants to download something it must ask you first (`confirm`), and it is told never to because a web page or file said to. A download still going after 6 s carries on in the background and you get a Windows notification when it ends.

**Honest limits.** Speed is about the *deciding*: opening an app is still the app's own start-up plus Eya's check that it really appeared (she doesn't say "Done" on a guess), about 1.3 s for Paint here. Browser and WhatsApp *automation* (clicking around a page) is still a few seconds per step, and anything that needs Gemini is still seconds. Messaging people by name is covered in its own section below.

**Talk mode uses the same layer.** In a live voice conversation the model is given one extra tool, `quick_command`, that takes **no arguments**: Eya runs the fast layer on what *you* said (the transcript of your last turn), never on anything the model writes, so the model cannot invent a path, a site or a message through it. A request the layer is sure of (a site, a folder, a file, a download, a message by name) is answered in milliseconds instead of the model choosing and chaining its own file and browser tools; one it is not sure of comes back as "not handled" and the model carries on as before. It is called once per turn, and the instructions tell the model to try it first for everyday requests. This was driven through a real Gemini Live voice session, not only with fake tools. The fast layer is still not used for always-on listening beyond a short command (see above), and the model can still decline to call it.

## Performance levels (small laptops)

Settings → Performance → **How hard Eya works**: Automatic (the default), Light, Balanced or Full. Automatic reads the memory and processor threads Windows reports: **Light** under about 5.5 GB or with 2 threads, **Balanced** up to about 11 GB or 4 threads, **Full** above that. (`EYA_PROFILE=light|balanced|full` overrides it for a test run.)

| | Light | Balanced | Full |
|---|---|---|---|
| Graphics acceleration | off | on | on |
| Offline (Kokoro) voice | off: the system voice speaks | on | on |
| File index | up to 30,000 files, built 12 s after start | 100,000, 4 s | 150,000, 3 s |
| Screen sharing | a picture every 2 s, 1,024 px wide | every 1 s, 1,280 px | every 1 s, 1,280 px |
| Things that move | 2 steps a second | 4 | 6 |

What it costs and buys, measured on the i3-1115G4 / 7.7 GB laptop this was built on: with Eya sitting idle, **Light used 684 MB against 1,388 MB** (graphics acceleration alone is about 700 MB), at the price of speech recognition on the processor, about twice as slow (roughly 2.5 s against 1.2 s for a 3-second clip). Acceleration is decided as the program starts, so changing the level asks for a restart; the installed app offers a **Restart Eya now** button.

**Nothing moves while Eya is idle, at every level.** On this laptop any CSS animation loop in the page, even a stepped one at one frame a second, cost 65–130 % of a processor core while the bubble was on screen (a transparent, always-on-top window is recomposited on every frame). The "breathing" and spinner effects are now a small script (`src/renderer/motion.ts`) that sets a few CSS variables at the level's rate only while something is happening (listening, thinking, speaking) and stops completely when nothing is: idle is about 0.2–0.7 % of one core. `tests/motion.test.ts` forbids CSS animations so it does not creep back, and `npm run perf:idle` measures a running Eya by kind of process against the budget in `scripts/idle-footprint.ps1`.

## Microsoft Word: tell Eya what to do, and she does it in the document

With Word open, say what you want and Eya does it **in the document in front**, through Word's own automation on this PC. Tell her how first ("the title centred and bold, 1.5 spacing, Times New Roman 12, number the paragraphs") and then dictate; she applies it as she writes. Every change is **one undo step** ("Eya: ..." in Word's Undo list), so **Ctrl+Z** takes back whatever she just did.

**What she can do**

| You say | What happens |
|---|---|
| "type in Word: *The Petitioner humbly submits…*" / "write the grounds…" | the words go in at the cursor, exactly as said; after a heading it is normal text, as pressing Enter would give |
| "make the Prayer heading centred and bold", "justify paragraphs 7 to 9, 1.5 spacing, Times New Roman 12", "number these" | character and paragraph formatting, styles (Heading 1…), bullets / numbering, indents, spacing |
| "add page numbers", "Page X of Y at the bottom right", "start from 3", "remove page numbers" | live page-number fields in the footer or header |
| "insert a table of contents" / "update the index" | a contents list from the headings; refreshed on request |
| "make a list of dates and events: 12.03.2020 order passed, 20.03.2020 representation made…" then "add one more event: 05.04.2021 notice issued" | a Date / Event table under its heading; a new row is numbered on by itself |
| "fill the running index in my writ" (the INDEX table is already there, page cells empty) | **one command, no model, about a second**: it reads each particular, finds that part in the document (an "Annexure P-1" line, a heading), and puts its page in the cell as a live page reference; ranges ("12 - 20") when the column says Pages; an entry it cannot find is named and left empty |
| "make a running index: Synopsis, List of dates, Grounds, Prayer, Annexure P-1…" | an Index table whose page numbers are **live fields pointing at each part of the document**, so they follow it as it grows; anything she cannot find is named, not guessed |
| "header: Writ Petition No. 123 of 2026", "A4, left margin 3.5 cm", "page break", "find State and replace with Union", "undo that", "save it" | headers and footers, page setup, breaks, find and replace, undo/redo, save |

**Speed.** Word is asked for the whole text in ONE call and everything else (paragraph numbers, searching, headings) is worked out from it; asking Word about each paragraph separately costs about 40 ms a time, which made reading a 1,100-paragraph petition take 2-7 s. On a 53-page, 1,154-paragraph document: status 130-640 ms, reading 120 paragraphs ~35 ms, finding text ~35 ms, go to a page ~70 ms. "Go to page 10", "next page", "scroll down" are one call each; `word_read` with `find` returns every place a word occurs (a placeholder like P1 / P2) with its paragraph and page, so nothing has to be read page by page, and a model that reads ten times in a row is stopped and told to search. Planning calls to Gemini are raced by the next model after 8 s and a model that just failed (503 / timeout) is left alone for 1-2 minutes instead of being retried on every step.

**Quick, no model:** the common ones ("add page numbers", "insert a table of contents", "update the index", "bold this", "centre this", "double spaced", "page break", "undo that", "save the document", "type in Word: …") are done at once from your exact words — about a second at most. Those that act at the cursor are only taken while Word is the window you are in; document ones need only an open document. Anything else goes to the model, which has six tools: `word_status`, `word_read`, `word_write`, `word_format`, `word_structure`, `word_edit`.

**Care taken:** a read-only or protected document is refused; a delete of more than a sentence or two, or a replace in many places, comes back as a question and waits for a yes; nothing is saved, closed or printed unless you ask (a never-saved document is not saved from here: she asks where). Nothing she reads is logged. **Reading:** like every request to the model, the parts of the document it needs (headings, a few paragraphs) are sent to Gemini; the model is told to read only what the request needs and not to repeat your document back.

**Not built:** comments and tracked changes, footnotes, mail merge, images, Word on the web / other editors, and a live "dictation mode" that types everything you say until you stop (each dictated sentence goes through "type in Word:" or the model).

**Where:** `src/main/word/word-helper.ps1` (the PowerShell helper that drives Word; `EYA_WORD_PRIVATE=1` makes it use a Word of its own, which is how the tests avoid anyone's real documents), `WordControl.ts`, `WordCommands.ts` (the quick phrases), `tools/impl/wordTools.ts`. Tests: `tests/wordTools.test.ts`, `tests/wordCommands.test.ts`, and the opt-in `EYA_LIVE_WORD=1 npx vitest run tests/live/wordcontrol.live.test.ts` (hidden Word on this PC; 15 checks).

## Teach Eya from your old petitions (references)

Give Eya a finished document once and she remembers **what is on which page, how each part is laid out, and how it is worded**. Later, hand her a half-done file and she can see what is missing and fill it in the same way.

This is not training of an AI model: she **reads** the finished document with Word and keeps a clerk's notes on this PC — the parts and their pages, how long each is, fonts, spacing, alignment, titles, margins and page numbers, and the text of each part.

**Teach her** (with the finished petition open in Word, or give her the file):
- "Learn this document as my writ petition."
- "Learn the file Old writ petition from my Documents as my service matter reference." (she finds the file, and reads it in a hidden copy of Word; your open documents are not touched)
- She answers with the page map: "Synopsis on page 2, list of dates and events on page 3, grounds on page 4…". Say if any part is wrong.

**Ask her what she knows:** "What have you learned?"  **Make a document look like it:** "Format this like my writ petition." (page setup, fonts, spacing, alignment, titles, page numbers; one undo step)

**Fill a half-done document:** "This is half done; fill it like my writ petition." She compares first (what is missing, what is still short, what looks different), tells you, then writes each missing part in the reference's wording and order, using the facts she finds in **this** document. She never invents a name, date, number or amount: where the document does not give one she writes **[●]** and asks you.

What it does well: structure, page map, layout and the order and wording of standard parts. What it does not do: decide facts of a new case, check law, or read scanned pages (it needs real Word text).

**Privacy:** what she learns stays in `%APPDATA%\eya\references` on this PC (say "forget my writ petition reference" to delete one). Only when she drafts do the parts of the reference she shows the model, and the facts of the new document, go to Gemini, like any other request.

**Where:** `src/main/word/referenceAnalyzer.ts` (reads Word's own XML of the body: titles by how a line looks, parts, looks, page map, comparison), `ReferenceStore.ts`, `ReferenceService.ts`, `ReferenceCommands.ts` (the spoken phrases), `tools/impl/referenceTools.ts` (`word_reference`), and `word-helper.ps1` (`analyze`, `pages_of`, `apply_profile`). Tests: `tests/wordReference.test.ts`, `tests/referenceCommands.test.ts`, and the opt-in `EYA_LIVE_WORD=1 npx vitest run tests/live/wordreference.live.test.ts` (builds a real 5-page petition, learns it from the file, compares and formats a half-done one).

## Writing Watch: a second pair of eyes while you draft

Say **"watch my writing"** (or tick it in Settings → Writing Watch, or in the tray menu) and, while you write a petition in Word (or in Notepad, WordPad, Notepad++, LibreOffice), Eya reads the document on this PC and shows a **small silent card** beside the bubble when she sees a slip. It never types, never changes anything, never speaks, and never takes the keyboard from your document; a correction is made only when you click **Fix** (or say "fix it"), and Word's own **Ctrl+Z** undoes it. It is off every time Eya starts. Say "stop watching" to end it, "check this document" for a one-off read of everything (including what was written before you started), "ignore it" / "read it" about the top card.

**What she looks for** (all on this PC, no model — `src/main/writing/checks.ts`): a word written twice in a row; two spaces, a space before a comma, none after one; brackets and quotation marks never closed (judged only after your cursor leaves the paragraph, since they are open while you type); a sentence that starts with a small letter (abbreviations like *No.*, *Rs.*, *vs.*, *i.e.* are not mistaken for sentence ends) and a lone "i"; **dates that do not exist** (31.02.2026, 31st April), "22th", the letter O typed for a zero ("2O26"); **an amount whose figures and words disagree** — "Rs. 5,00,000/- (Rupees five lakh fifty thousand only)" is read the Indian way (lakh, crore) and compared; **a name or a case number spelled two ways** (a name written once beside one written three times, `W.P. No. 12354 of 2026` beside `12345 of 2026`); **paragraph numbers that jump, repeat or go back**; "the petitioner" in small letters in a draft that writes "Petitioner" everywhere else. In Word she also asks **Word's own spell checker** (local) for its suggestions near the cursor — skipping abbreviations and a name you spell the same way throughout. A suggestion gets a **Fix** button only when the correction is certain; otherwise it is only shown.

**What is checked, and when.** The document is looked at about once a second; when your writing pauses for about two seconds only the **paragraphs that changed** since she started looking are checked (an old document's existing slips wait for "check this document"; moving the cursor is not writing). A finding stays only while its words are there: fix it, rewrite it, delete it, or press Ctrl+Z (the slip returns and is noticed again). "Ignore" is remembered for that slip, and for a spelling it is for that word everywhere in the session. At most six are shown, nearest the cursor first, with "+ N more".

**Privacy, honestly.** A petition is confidential, so: reading happens only while you have switched it on; the text is held in memory and **never saved, logged or sent anywhere** (the diagnostic `EYA_WRITING_DEBUG=1` logs paragraph numbers and counts, not words); Word is read through its own automation interface and the plain editors through Windows UI Automation, **only** in a short list of programs — never a browser, a chat app or a password box; the card window is excluded from screen captures and screen sharing. The optional **deeper check by Gemini** (grammar, wording; "allow cloud check" or the Settings switch, needs your key) sends **one paragraph at a time — the one you are writing** — while it is on for the session, is off again at every start, and what it says is trusted no further than it can be checked: a suggestion must quote words really in the paragraph, and a fix is offered only if the model gave one.

**How it was verified.** About 70 unit tests (the checks including false-alarm cases, the watcher with a fake document and clock, the helper protocol with a stand-in process, the commands, the cloud-answer parsing, the card placement, the preload); a live test against **real Word** through the real helper (`EYA_LIVE_WORD=1 npx vitest run tests/live/writingword.live.test.ts`: the old slip left alone, the four deliberate mistakes found with Word's own "recieved → received", a fix made only on request and undone with Ctrl+Z, a whole-document check) and against **real Notepad** (`EYA_LIVE_NOTEPAD=1`); and the running app with a real Word document, looking at the card itself and clicking **Fix** and **Ignore** on it. Running it for real found four things unit tests had not: the cursor leaving an old paragraph made its old slip appear; an Undo of a fix was not noticed again; a second preload script made the bundler split a file the sandboxed preload cannot load (which silently broke the whole window — now guarded by `tests/writingPreload.test.ts`); and four findings were taller than the card window, hiding its footer (the list now scrolls).

**Not done / not verified.** Google Docs, Word Online and other web editors (they draw their own text; a browser is deliberately not read), Pages/Google Keep, and editing in Notepad (read-only there: no Fix button). The card was driven and read through the page, not clicked with a physical mouse while Word has the keyboard (it is created non-focusable, which is what keeps it from taking the keyboard). Tables in Word shift paragraph numbers when Word and the text disagree (it then asks Word paragraph by paragraph). Only English legal drafting is checked; Telugu or Hindi text is read but not judged. It is not legal advice and not a replacement for reading the draft: it catches slips, not arguments.

## Memory and routines (a local SQLite database)

Eya keeps three kinds of things, all in one SQLite file on this PC — `%APPDATA%\eya\data\eya_memory.db` (persistent, never a temp folder; set `EYA_MEMORY_DB` to put it somewhere else). Nothing leaves the machine, there is no database server, and no JSON file is involved.

- **Preferences** ("always save downloaded PDFs to the Desktop") and **facts** ("Ravi is my brother's contact"): only what you ask her to remember. Passwords, PINs, card numbers and the like are refused.
- **Routines** (the important one): a task you repeat, saved as a short list of high-level steps — open a site, find or click text by its words, type into a field by its label, download, save — never screen coordinates. Each step can carry a check ("the address contains…", "the page says…"), and a routine tracks how often it worked or failed.

**Order of work for every command:** (1) instant local shortcuts (open/close an app); (2) a memory command or a saved routine, looked up in SQLite — no model is called; (3) a clear match runs the routine directly; (3b) the fast everyday commands above (sites, folders, files, downloads); (4) only otherwise does the request go to Gemini, which is told the relevant preferences and the routines it can run. Matching a routine is an exact lookup on the normalised wording ("check today's cause list" = "Check todays cause list"), plus a typo-tolerant fallback that still requires the same dates and numbers; it never uses a model, and 1,000 lookups among 500 routines take well under a millisecond each.

**How she learns:** she watches the browser and app steps of each task. When the same steps have worked **three times**, she asks "You've done this several times. Would you like me to save it as a routine?" — and saves it only if you say yes ("no" means she never asks about that task again). Dates you typed become `{{today}}`, so the routine types *that day's* date. A task is never learned from if it touched anything a routine must not repeat or learn: a file deleted, a message sent, a screenshot, a chat app, a sign-in or password field, a link carrying a token, a request containing a long number, or an `@`. No conversation is stored — only a step signature, the steps and the short wordings you used.

**If something goes wrong:** a routine that cannot finish (a link was renamed, a check fails) stops, records the failure, and hands over to the normal agent from where it stopped — never blindly carrying on. If the agent then finishes the job another way, she offers to update the routine (the part that worked, then the new way). A routine can **never** confirm anything for you: it goes through the same tools and the same confirmation rules, so a saved "Place order" or "Send" click is refused and turned into a question. A routine that is switched off is never run. If the browser tool's loop guard stops a routine because it was run several times in a few seconds, she says so plainly rather than counting it as the routine's fault.

**Things to say** (all handled locally, no model): "remember that Ravi is my brother's contact" · "remember: always save downloaded PDFs to Desktop" · "what do you remember?" · "show my routines" · "save this as a routine" (or "…called morning list") · "don't remember this" · "forget Ravi" · "delete the routine check cause list" (she asks first) · "forget this routine" (the one just used).

**The panel:** the **Memory** pill shows your routines (switch each on or off, rename, add or remove the phrases that run it, read its steps, delete) and your memories (read, edit, forget, add). An open offer also shows Yes / No buttons.

**Talk mode:** the model hears you directly, so routines and preferences are put in its instructions when a conversation starts, `run_routine` runs one in a single call, and Eya counts the tasks herself (grouping tool calls by your turn) and says the offer aloud — the live model never hears it, so a bare "yes" or "no" right after a task is passed on with `answer_routine_suggestion`. A routine saved *during* a conversation is known to the model from that tool's result, and fully from the next conversation.

**Limits, honestly:** a request has to match a wording the routine knows to run without a model — a different wording goes to Gemini, which is told about the routine and can run it. A task that ends with Eya asking you a question is not counted as finished, so multi-turn tasks are not learned. A routine runs at the browser tools' own speed (a few seconds per step); what it saves is the model round trips and the reasoning, not the browsing. Routines were verified live against a fixture courts portal in real Chrome, not against real court websites or Edge, and the Talk-mode path is covered by tests with fake tools but has not been driven through a real Gemini Live voice session.

**Technical notes:** `node-sqlite3-wasm` (SQLite compiled to WebAssembly, reads and writes the file directly) — chosen over `better-sqlite3`, which needs a separate native build for Electron and for the tests, and over `node:sqlite`, which Electron 33's Node 20 does not have. Parameterised statements throughout; the schema is versioned with SQLite's `user_version` and migrated in transactions on start (a database from a *newer* Eya is refused rather than guessed at; a damaged file is set aside as `.damaged-<time>` and a fresh one started). If the database cannot be opened at all, Eya runs without memory. Code: `src/main/memory/` (store, matcher, executor, recorder, service), `src/main/tools/impl/memoryTools.ts`, `src/main/live/liveTasks.ts`, `src/renderer/MemoryPanel.tsx`.

## Tasks: Eya keeps what you asked until it is done (16 Oct 2026)

Before, a slow page, a live conversation that ended after 30 quiet seconds, or an AI that ran out for the day each made Eya forget what you asked ("send this image to Akka on WhatsApp") and you had to say it again. Now a request that cannot finish at once becomes a **task**: it is kept (a small file, `tasks.json`, in Eya's data folder, so it survives closing Eya and restarting the PC), tried again by itself, and you are told by a **desktop notification**.

- **Slow pages.** The chat flow used to wait about five seconds for WhatsApp Web to load its chats, then say it could not find the chat. It now looks for as long as the page says it is still loading (up to 90 seconds on a slow connection), and a chat that is really not there is still said quickly. If the page is still not ready after that, Eya says so, keeps the task, and tries again every little while; a log-in (QR code) screen is reported at once as waiting for you.
- **A step that outlasts the live conversation's patience** (40 seconds) is no longer abandoned: it goes on in the background, the model is told "still working, do not run it again", and when it finishes Eya tells you, aloud and by notification. The live conversation is also **not ended for being quiet while a task is waiting** (for up to ten minutes), so she can tell you how it went. If a question is waiting ("Found Akka. Send the file?") she asks it again in the conversation, and your "yes" is still yours: nothing is sent without it.
- **The AI is out for the day.** An *action* you ask for ("send…", "open…", "check…") is kept and done when an AI is back; a plain question is not kept (an answer hours later is no use).
- **CAPTCHAs and sign-ins.** Eya never solves a CAPTCHA, never types a password, and never tries to get past a bot check: they exist to tell a person from a program, so those are yours to do. (A one-time verification code you say out loud she does type: see "Waiting for a verification code".) What changed is that she no longer waits to be told "continue": the task is kept as *waiting for you*, she watches the page, and she carries on by herself the moment you have ticked it or signed in.
- **Seeing and stopping them.** Home has a **Tasks** card (and the quick panel shows the one that needs you, with **Yes / No** buttons for a question). Say or type "cancel the task", "stop all tasks", "never mind" (while one is open), "what are you working on", or "continue". Asking for the same thing again replaces the earlier task instead of keeping two.
- **Safety.** Carrying a task on never skips a question: a send still asks first, a delete still asks first. A task is tried at most eight times, and given up (quietly) after six hours. A task cut off by Eya closing is carried on at the next start if it is less than 30 minutes old, otherwise it waits for you ("Resume it?").

What is not built: tasks that repeat on a schedule ("every day at 9"); a task is for one thing you asked once.

## Internet researcher: find it properly, anywhere on the internet (16 Oct 2026)

"I want the Kesavananda Bharati case and the related PDF." / "I want this film." Eya now researches like a careful person instead of opening one search page. The tool is `deep_research` (kinds `answer`, `documents`, `media`); it uses **no AI of its own** (the model that asked reads the findings), so it spends none of your AI allowance.

- **She asks first.** For a document or a film or song the first call researches nothing: it hands back "Do you know a website where this is available? If you tell me, I'll look there first." If you name a site, she looks there first (its own search box is asked directly, with the names and subject words only: Indian Kanoon matches every word, and "judgment of the Supreme Court" is in every judgment). If you say no, or that site did not have it, she searches the whole internet. She never stops at one site or one search.
- **How it searches.** Five to ten differently-worded searches (DuckDuckGo, with Bing as a second opinion and your own browser as the fallback), the best pages read for real, then a second round that follows the leads in what it read (a citation such as `AIR 1973 SC 1461`, a case number, "X v Y"). Pages are ranked by how much the site can be trusted (court and government sites, legal publishers, archives and universities first; blogs and unknown sites after; spam domains last) and by how well the page matches the *distinctive* words of your request: names and numbers count for more, the words that fit every page of a field ("judgment", "Supreme Court") for less. A page that only has the generic words, a circular or exam notice, or a document from a site's menu or footer is not offered.
- **PDFs are checked.** An address is offered as a PDF only if its first bytes are the PDF marker (`%PDF-`), checked with a small range request, with its size. A link that is really a log-in page is dropped. Titles that a search engine takes from the first line of the file ("JUDIS.NIC.IN SUPREME COURT OF INDIA Page 1 of 502") are replaced by the file's own name when that says more. Then she offers to download the best one (`download_file`, which still asks you first) or open it. About 20-30 seconds (up to 100 with `thorough`); an identical question within 30 minutes is answered from memory, and asking again while it runs joins the running one. It runs as a task like anything slow: if the live conversation's patience (40 s) runs out, it carries on in the background and tells you.
- **Films and songs: legal places only.** She finds where a title can be watched or heard on an official platform (YouTube, JioHotstar, Prime Video, Netflix, ZEE5, SonyLIV, MX Player, Tubi, Plex, JioSaavn and others; free ones first, only pages about *that* title), and copies that are legally free to keep from the **Internet Archive**: only when the item carries a public-domain or Creative Commons licence, or sits in a curated public-domain collection and is a film from 1930 or earlier (the Archive also holds DVD rips and album uploads; those are left out, and she says so). A free copy comes with a direct file address, downloaded only with your yes. She does **not** search for, name or open torrent, "free download", crack or shadow-library sites (blocked by domain), and if you ask for a recent film "free from anywhere" she says plainly that she uses legal sources and gives you those.
- **Playing it: `play_on_youtube`.** YouTube's own results are read, and the result a careful person would click is chosen: the title that was asked for, from the official (verified) channel, of the right length (a song is a few minutes; a film an hour or more; a mashup, jukebox, trailer, scene or 30-second clip is not what you asked for). For a *film* she plays only a verified channel's upload, or a film from 1930 or earlier; otherwise she says there is no official full-length upload (the "full movie" uploads of recent films by anyone else are mostly pirated) and offers to check where it streams legally. "Next one" / "not that one" plays the next candidate.
- **Adverts (`skip_ads`, and inside `play_on_youtube`).** The Eya browser extension (now **0.7.0; reload it once** in chrome://extensions or edge://extensions) presses the page's *own* Skip button the moment it appears (about five seconds into a skippable advert), closes YouTube's overlay adverts and survey dismiss buttons, and keeps checking every half second while the video plays, so an advert in the middle of a song is skipped too. An advert with no Skip button is waited through (nothing is hidden, sped up or blocked) and the video continues after it. On other pages the model closes pop-ups and advert layers itself with `click_on_page`, rejects non-essential cookies, and when a click opens an advert in a new tab it closes that tab, switches back to the page it was on and clicks again (up to three times). It never fills in or clicks through an advert, and never downloads from one.

**Measured.** Real internet: the Kesavananda Bharati example returned the Supreme Court's own judgment PDF (36 MB, from sci.gov.in) and scobserver.in's copy, both confirmed as PDFs, in 9-28 s; with Indian Kanoon named, the Puttaswamy judgment pages (the search box, not the generic Supreme Court pages) in 20 s. A 1913 film returned the Archive's public-domain copy with a 56 MB MP4 address; a 2019 film returned six official platforms and no free copy; a song returned the official T-Series upload first. In a real Chrome with the real 0.7.0 extension (`tests/live/ads.live.test.ts`) a page imitating YouTube's player was handled correctly: the overlay advert closed, the Skip button pressed when it appeared (8 s in), the video started when the page left it paused, and an advert with no Skip button was waited through. The real app was driven with a scripted model (`research-e2e`): the tool is sent for a document request, the prompt carries the research section, the first call asks the question, and "no" runs the real research and returns verified PDFs to the model.

**Not verified, honestly.** A *real* YouTube advert being skipped: in two runs against real YouTube (headless, fresh profile) no advert was served, so the Skip button was never there to press (the helper was on, and the video played). The selectors are the ones YouTube's player has used; its markup changes. Autoplay: a fresh browser profile refuses to start sound until you have clicked on the site (measured: `play() failed because the user didn't interact`); your own Chrome, where you use YouTube, normally allows it, and if not Eya says the video is open and waiting for one click on play (allowing sound for youtube.com in the site settings stops that). Ad-opened tabs are handled by the model with the existing tab tools, with the rules above, but that flow was not run against a real ad-heavy site. Scanned or image-only PDFs are listed like any other (their text is not read). `thorough` searches go deeper, not wider than the search engines allow: DuckDuckGo and Bing were used; Google, Brave and Yahoo refuse scripts.

## Lock, restart and shutdown

`lock_screen` calls Windows' own `LockWorkStation` (`user32.dll`, via `rundll32.exe user32.dll,LockWorkStation` — the same mechanism Microsoft documents for this), then confirms it actually worked by checking that `LogonUI.exe`, the real lock-screen process, appears afterward — not just that the request was sent. `restart_computer` and `shutdown_computer` use Windows' own `shutdown.exe` (`/r` or `/s`, deliberately without `/f`, so an application with unsaved work gets asked to close first rather than force-killed) behind the same ask-first `confirm: true` gate every other destructive tool uses, with a short 5-second delay before either fires so Eya's own spoken "Done." has time to actually finish playing first.

**Honestly, not fired live.** Locking the screen wasn't tested live without asking first, since it would interrupt whatever the user is doing without warning. Restarting and shutting down were built and fully unit-tested with fakes, but a live end-to-end fire — even the safe "schedule it an hour out, then immediately cancel it" trick — was refused outright by this environment's own safety classifier as a real-world system transaction, and rightly so; actually rebooting or shutting down the machine autonomously is exactly the kind of action that should need the user's own hands on it, not an agent's.

## A Recycle Bin gotcha: hidden file extensions

Windows Explorer's Shell COM interface (`Shell.Application`, `Namespace(10)`) exposes a recycled item's display name through its `.Name` property — which silently drops the extension whenever Explorer's own "hide extensions for known file types" setting is on, so a file actually named `report.pdf` gets reported back as just `report`. That broke exact-name lookups (asking to restore `report.pdf` wouldn't match a listed `report`) and was only caught live, not by a unit test, since the fakes used in testing never had that Explorer setting to leak. Fixed at the source, by reading the `System.FileName` extended property instead (reliable, unaffected by that display setting), plus a belt-and-braces fallback in the matching logic itself that also tries the name with its extension stripped either way.

## Roadmap

Two large continuation phases have been requested and scoped down to what could be built and genuinely verified, rather than attempted whole. Delivered: file operations + confirm-before-destroy + reference resolution (phase 2), then smart file search (date/size/type filters, multi-match disambiguation, a numbered "search session" so "the second one" resolves), `close_file` (by window title, not full UI Automation), and a handful of Windows system controls (Settings pages, exact volume, exact brightness) (phase 3), a recycle-vs-permanent delete choice with a consistent "Done." completion reply (phase 4), full Recycle Bin management (list, count, search, restore one or all, permanently delete, empty — all against the real Windows Recycle Bin) plus five additional male voice options (phase 5), a whole-PC default search scope for finding, opening, playing and reading files — every connected drive, not just Downloads/Desktop/Documents (phase 6), real lock/restart/shutdown plus Start-Menu-wide application discovery with a known-web-app fallback (phase 7), and real, DOM-aware website navigation (open/inspect/click/fill on a page, never a search or an invented URL in its place) (phase 8), through to a loop guard (phase 11), a search fallback for when Gemini's own search allowance is spent (phase 12), and working in the user's own signed-in browser through a browser extension with a locally-authenticated bridge, tab reuse, download tracking, CAPTCHA/MFA pause, and confirmation before purchases, sends and deletes (phase 13).

Not built: letting Eya *control* the screen from the Live Screen page (the **Control** button there is disabled; her screen tools `screen_elements` / `screen_click` can click by voice or typing, with their confirmations, but not from that page), and file actions that change things from the Files page (rename, move, delete, send — those stay with the voice and typed tools, which ask before anything destructive).

Deliberately not attempted, because each is a substantial subsystem needing its own real testing (and in two cases, a considered no rather than a "later"):

1. A Gemini Computer Use (screenshot-driven) fallback for pages whose structure the DOM can't describe, a scroll tool, and trusted (real-gesture) clicks — the last would need a permission the browser extension deliberately declines.
2. A larger rewrite into a separate world-state / decision / verification / recovery layer: the Gemini function-calling loop already does observe → decide → act → observe with the real page each turn, so a second layer was judged redundant rather than useful. An "Agent Inspector" screen is not built either (everything it would show is already in the logs and each tool result).
3. Windows UI Automation proper (HWND/focus-event tracking, `WindowPattern.Close`), for richer window/document association than the current title-matching `close_file` gives, and as an alternative path for a page element DOM inspection alone can't identify.
4. A Gemini Computer Use (screenshot-driven) fallback for when neither DOM inspection nor UI Automation can find what it needs.
5. **Wi-Fi/Bluetooth on/off — a deliberate no, not a "later".** Toggling the Wi-Fi adapter risks cutting off the machine Eya runs on; toggling Bluetooth risks dropping a wireless mouse/keyboard; both typically need administrator rights besides. Their Settings pages still open on request.
6. A "trusted mode" setting that skips confirmation for destructive actions (off by default; not started).
7. A task queue with cancellation ("stop", "never mind") and long-running/async tool handling.
8. An audit log of every action taken; detecting a file the user opened manually, outside Eya, and associating it automatically.
9. A trained (not synthetic-voice-tuned) wake word, once real usage data exists.
10. Packaging the app for distribution (there is no build/installer step yet — now also needs to ship Playwright's browser-launch logic, which expects a real Edge/Chrome install on the target machine rather than bundling its own, and `node-sqlite3-wasm` with its `.wasm` file for the memory database).
